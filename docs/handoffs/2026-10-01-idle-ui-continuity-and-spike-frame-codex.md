# 경기 전환 중 메뉴 유지 + 발동 후 72ms 프레임 조사 — Codex 요청

사용자 승인(2026-10-01): 아래 1·2 모두 진행. 1은 **게임 동작 변경**(사용자 승인 범위), 2는 **조사·측정 우선**(수정은 결과 보고 후 승인).

## 1. 경기 전환(SETUP) 중 관리 메뉴·창 유지

### 1-1. 요구

방치형 게임이므로 **경기 진행과 관계없이 관리 버튼과 메뉴를 계속 조작할 수 있어야 한다.** 자동으로 다음 경기가 시작돼도 사용자가 열어 둔 관리·리그 맵·차고·인벤토리·엔트리 설정 창이 닫히거나 관리 버튼이 사라지면 안 된다.

### 1-2. 현재 (Codex 확인 + Claude 읽기 전용)

- 기준 코드에서도 새 경기 SETUP 중 관리 버튼이 숨겨지고 관리·리그 맵 창이 닫힌다.
- `_update_season_map_button()`은 `_race_state != SETUP`일 때만 버튼을 보이고, 숨김 분기에서 `_close_management_popup()`을 호출한다. `_start_race_with_track()`의 SETUP 구간(Static Ribbon·날씨 준비 뒤)에서도 호출된다.
- 반면 `_refresh_open_management_popups_after_race_restart()`는 경기 재시작 뒤 **열려 있는** 관리·종료 확인·엔트리 설정·차고·부품 인벤토리·리그 맵 창을 위치·내용 갱신하도록 되어 있다 → **창을 유지한 채 갱신하는 것이 원래 의도**로 보인다. SETUP 숨김 처리가 그 전에 창을 닫아 버려 이 갱신이 무력화되는 것으로 추정.

### 1-3. 요청

1. **자동 진행(경기 종료 → 다음 경기, 반복 주행 등)**으로 SETUP에 들어갈 때 관리 버튼을 숨기지 않고 열린 창을 닫지 않는다. 경기 데이터가 바뀌는 시점에는 기존 `_refresh_open_management_popups_after_race_restart()`로 내용만 갱신.
2. SETUP 중 메뉴 조작이 경기 준비와 충돌하는 기능(예: 준비 중인 경기의 편성·차량 변경, 경기 시작/중단 버튼)은 **기능만 잠시 비활성(또는 다음 경기 반영)**으로 처리하고 창은 유지. 충돌 여부와 처리 방식을 기능별로 보고.
3. **사용자가 직접** 리그 맵에서 다른 경기를 선택하거나 경기를 중단(`_abort_current_race`)하는 경로는 기존 동작(선택한 창 닫기)을 유지해도 된다 — 경로별로 구분해 보고.
4. 시작 화면 복귀(`_return_to_start_screen`) 등 레이스가 없는 화면 전환은 범위 밖.

### 1-4. 검증

- 관리 창·리그 맵·차고·인벤토리·엔트리 설정·설정 창을 각각 열어 둔 상태로 자동 다음 경기 전환 → 창 유지·내용 갱신·조작 가능, 관리 버튼 계속 표시.
- SETUP 중 클릭·스크롤·탭 전환 가능, 준비 취소·실패 시에도 창 상태 정상.
- 위젯 입력 영역(`_sync_widget_input_regions`)이 열린 창을 포함하는지.

## 2. 발동 후 72ms 프레임 원인 조사 (측정·분석만)

### 2-1. 현황

- 컷인 준비 수정 후 조건 A: 발동 직후 18.12ms, 동기 CPU 6.40ms, **발동 후 2초 내 최대 72.27ms**(해당 프레임에 컷인 초기화 없음).
- 이전 관측: MP4 제외(B)에서 발동 약 1초 뒤 67.37ms, 발동 전에도 별도 67.11ms.
- → 컷인과 무관한 **주기적·지연 실행 작업**일 가능성.

### 2-2. 후보 (Claude, 미검증)

1. **CPU 호환 파티클 풀 지연 확장**: 첫 발동 시 16슬롯, **0.5초 뒤 추가 88슬롯을 한 번에 생성**(이전 조사 결과). 노드 생성·`add_child`가 한 프레임에 몰리면 큰 비용 가능. 발동 1초 전후 67~72ms와 시점이 가까움.
2. 자동 저장·진행도 저장, HUD/리더보드 전체 재구성, GC·리소스 해제, 텍스처 업로드.
3. 발동 전 67ms는 1과 무관 → 2의 주기 작업일 가능성.

### 2-3. 요청

- 기존 `TalentActivationSpikeProbe.gd`로 큰 프레임(>30ms)마다 **프레임 안 구간별 CPU**(파티클 풀 생성 수·시간, 저장, HUD/리더보드, 날씨·타이어 VFX, GC 가능 범위)를 기록.
- 풀 확장 시점(발동 후 0.5s)과 큰 프레임의 일치 여부. 재발동(풀 재사용) 시 사라지는지.
- 발동이 없는 구간의 주기적 큰 프레임 여부(발동 전 67ms 재현).
- 결과에 따른 대응 제안: 풀이 원인이면 **편성된 재능 package의 파티클 풀을 SETUP에서 미리 생성**(기존 준비 경로, 레이스 간 재사용) 또는 확장을 여러 프레임에 분산. Studio package·계약 변경은 필요 없을 것으로 예상(필요하면 먼저 알려 달라).
